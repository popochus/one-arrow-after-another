## 二、项目介绍

### 2.1 游戏规则

棋盘上散布着朝上、下、左、右四个方向的箭头。玩家每次点击一个箭头，程序检查它朝向的那条线上、到棋盘边界之间还有没有别的箭头：

- **前方没有阻挡**：箭头沿朝向飞出棋盘并消失；
- **前方有箭头阻挡**：箭头留在原地，给出反馈，并消耗一次失误机会。

清空本关全部箭头即通关；失误次数（每关 3 次）耗尽则本关失败。

```
→  ·  ·  ↑  ·        朝右的箭头右边还有箭头，不能飞出
·  ·  ·  ·  →        朝右的箭头右边到边界空无一物，可以飞出
```

作业限定了基础版只做单格箭头，所以路径检测**只需要判断同一行或同一列**，不用考虑斜向。这一点我在实现时严格守着，没有自己加规则。

### 2.2 界面设计

界面按手机竖屏比例（720×1280）设计——原始游戏和同学做的同类作品都是竖屏，横屏看起来不像小游戏。共有五个画面：

| 界面 | 内容 |
| --- | --- |
| 开始界面 | 标题、玩法一句话说明、四个方向的示例箭头、「开始游戏」；有进度时额外出现「继续游戏 · 第 N 关」 |
| 关卡选择 | 五张关卡卡片，显示序号、主题名、状态（已通关 / 剩余箭头数） |
| 游戏界面 | 顶部显示关卡名、剩余箭头数、失误次数；中部棋盘；底部分两行按钮——上行「撤销 / 提示」，下行「主菜单 / 重新开始」 |
| 通关结算 | 「过关！」或「全部通关！」+「主菜单 / 重玩本关 / 下一关」 |
| 失败结算 | 「失误次数用完了」+ 已清除 / 剩余数量 +「主菜单 / 重试本关」 |

720×1280 是**逻辑画布**的尺寸，不是窗口的尺寸。这一点是后来改的：在 1080p 屏幕上实测发现，去掉任务栏后可用高度只有 1032 像素，窗口比屏幕高出 248 像素，Windows 只能把它整体上移，结果标题栏被顶到屏幕外——顶部文字被裁掉一半，而且没有标题栏可抓，窗口也拖不动。修复方式是启动时读一次屏幕可用区域算出缩放比例（本机为 0.77，窗口变为 554×984），所有绘制照旧发生在 720×1280 的逻辑画布上、最后整体缩放到窗口，鼠标坐标再反向换算回逻辑坐标。这样界面代码一行都不用重排，屏幕够大时还会自动保持 1:1。

### 2.3 主要功能

- **四方向箭头与路径判断**：四种方向齐全，同行同列阻挡判断与边界处理正确；
- **飞出与碰撞反馈**：飞出 0.55 秒并淡出；碰撞时箭头变红、左右晃动 0.34 秒（幅度 9 像素），顶部弹出文字提示；
- **失误机制**：每关 3 次机会，顶部实时显示；
- **5 个关卡**：难度递进，全部经求解器验证可通关；
- **完整流程**：开始 → 选关 → 游戏 → 结算 → 下一关，支持重新开始、返回主菜单、继续游戏；
- **关卡选择**：任意关卡可直接进入，已通关的标绿色「已通关」；
- **撤销与提示**：撤销把棋盘和失误次数一起退回上一步，可连续撤销，没有历史时按钮置灰；提示高亮一个当前确实能飞出的箭头。另配键盘快捷键 `U` / `H`；
- **四声音效**：飞出 / 碰撞 / 撤销 / 通关各一个音，全部由代码合成波形，不引入任何音频文件；
- **判定后锁定输入**：胜负一经判定，棋盘与辅助按钮立即停止响应（这条是踩坑之后补的，见 5.3）。

### 2.4 特色

和"能跑就行"的实现相比，这个项目多做了三件事：

1. **关卡可解性是算出来的，不是试出来的**。作业把「关卡实际上无法通关」列为明确扣分项，所以我写了一个贪心求解器自动校验每一关，还写了一个生成器专门构造必然可解的布局（见 3.3）。
2. **每一步都留了真实的过程记录**。项目根目录有一份 `DEVLOG.md`，每次和 AI 协作完就当场追加一条，记录了提了什么要求、AI 给了什么、我改了什么。博客第五节的素材全部来自它，不是事后回忆的。
3. **全流程可自动化复现**。一条命令跑完 30 项测试并生成 Markdown 报告，另有脚本自动生成全部界面截图和演示动图——文档里的图片和数据都可以随时重新生成，不靠手工截图。

## 三、实现思路

### 3.1 箭头与方向的表示

一个箭头就是**一个格子加一个方向**，用不可变的数据类表示：

```python
@dataclass(frozen=True)
class Arrow:
    row: int
    col: int
    direction: str      # 'up' / 'down' / 'left' / 'right'
```

方向不存成角度或向量，而是存成字符串，再通过一张映射表换算成行列增量：

```python
DIRECTIONS = {
    "up": (-1, 0),
    "down": (1, 0),
    "left": (0, -1),
    "right": (0, 1),
}
```

这样做的好处是：**方向本身可读**，调试和测试输出时直接打印 `'up'` 就懂；而所有涉及坐标运算的地方都统一查 `DIRECTIONS`，不会出现"向上是 row-1 还是 row+1"记混的问题。

棋盘内部用字典以 `(row, col)` 为键存箭头，键就是坐标，取某个格子的箭头是 O(1)，消除时直接删键即可。同时保留一份初始布局副本，供「重新开始」复原。

### 3.2 路径检测（核心）

这是整个游戏最关键的一段代码，也是作业评分权重最高的一块（25 分）。

```python
def can_fly_out(self, arrow):
    """判断箭头能否飞出棋盘。"""
    d_row, d_col = DIRECTIONS[arrow.direction]
    row = arrow.row + d_row          # 从箭头的"下一格"开始
    col = arrow.col + d_col

    while self.is_inside(row, col):  # 还在棋盘内
        if (row, col) in self._arrows:
            return False             # 撞到箭头 -> 被阻挡
        row += d_row
        col += d_col

    return True                      # 一路走到棋盘外 -> 畅通
```

思路是**从箭头沿朝向逐格往前走**：中途只要碰到任何箭头就判定被阻挡，一路走出棋盘则判定畅通。

这里有一个刻意的设计：把越界判断单独抽成 `is_inside()`，作为循环条件：

```python
def is_inside(self, row, col):
    return 0 <= row < self.rows and 0 <= col < self.cols
```

如果不这样写，四个方向就要各写一遍"上边界 / 下边界 / 左边界 / 右边界"的判断，四份代码里的边界条件只要有一处写错（比如 `<` 写成 `<=`），就会出现**数组越界或误判贴边箭头**——这正是作业示例里 `fix: 修复向上检测时的数组越界` 那类问题。收敛到一处之后，边界只有一种写法，测试也只需要覆盖一遍。

**边界情况我专门测了**：1×1 的棋盘上，四个方向的箭头都应该能直接飞出；贴边且朝向棋盘外的箭头不应该报错。这 9 项用例保留在 `tools/run_tests.py` 里，可以随时复跑。

### 3.3 关卡如何表示与校验

关卡用**字符画**描述，一个字符代表一个格子：

```python
_RAW_LEVELS = [
    (
        "第 1 关 · 顺藤摸瓜",
        """
        >  >  >  .  ^
        .  v  .  .  .
        .  .  .  <  .
        .  v  >  .  .
        .  .  .  .  .
        """,
    ),
    # ...
]
```

`^` 向上、`v` 向下、`<` 向左、`>` 向右、`.` 空位。选这种格式是因为它**肉眼就是一张棋盘**，改关卡时不用去数组里数个位，一眼就能看出布局和依赖关系。

五个关卡的设计意图如下：

| 关卡 | 主题 | 箭头数 | 设计意图 |
| --- | --- | --- | --- |
| 1 | 顺藤摸瓜 | 8 | 教学关，出口明显 |
| 2 | 层层推进 | 10 | 引入纵向依赖（先清下面才能放走上面） |
| 3 | 从两端突破 | 10 | 上下两排必须从两端往中间逐个清，考顺序感 |
| 4 | 四面楚歌 | 14 | 可飞位置分散在四周 |
| 5 | 天罗地网 | 14 | 首轮只有少数箭头能飞，依赖链最长 |

**关键问题：怎么保证每一关真的能通关？**

作业把"关卡实际上无法通关"列为扣分项。靠手工试玩容易漏（试通了第 1 关不代表第 5 关没问题），所以我没有靠试，而是先推导了一条性质：

> 消除一个箭头只会让棋盘上的障碍变少，绝不会让原本能飞出的箭头变得飞不出去——也就是说，"能否飞出"这个性质对消除操作是**单调**的。

由此得到一个结论：**贪心地反复消掉当前所有能飞的箭头，如果最后能清空，关卡就可解；如果中途无箭头可消，就说明有箭头互相锁死，关卡无解。** 完全不需要搜索，一遍循环就能判定：

```python
def solve(board):
    work = Board(board.rows, board.cols, board.arrows)   # 复制，不改原棋盘
    order = []
    while work.remaining:
        removable = [a for a in work.arrows if work.can_fly_out(a)]
        if not removable:
            return None          # 死锁，关卡无解
        for arrow in removable:
            work.remove(arrow)
            order.append(arrow)
    return order                 # 顺带得到一条合法通关顺序
```

这条推论还有个附带好处：`solve()` 返回的就是一条**合法通关顺序**，测试脚本里通关类用例的点击步骤直接由它现场算出，不用手工写死——以后改了关卡，测试依然有效。

校验只是"事后检查"，万一设计出无解的关卡还是得返工。所以我又写了一个**生成器**，用"反向放置"直接构造必然可解的布局：从最后一个被消除的箭头开始，倒着往棋盘上放，每放一个都要求它到边界之间没有已放置的箭头——这样构造出来的布局天然对应一条合法通关顺序，**必然有解**。

生成器先产出 4000 个布局，再用求解器独立复验，**全部可解**，说明这套推导是成立的。前 3 关我手工设计（依赖关系一眼看得懂），后 2 关从生成结果里挑箭头更多、依赖链更长的。

校验结果可以随时复跑：

```
$ python tools/verify_levels.py
结论：全部关卡均可通关（共 5 关）
```

### 3.4 项目结构

```
one-arrow-after-another/
├── main.py                 程序入口
├── run_game.bat            一键启动（双击即可）
├── run_tests.bat           一键测试
├── game/
│   ├── config.py           窗口、网格、配色、动画参数、字体
│   ├── board.py            箭头模型 + 路径检测（核心）
│   ├── levels.py           关卡数据（字符画）
│   ├── solver.py           贪心求解与可解性判定
│   ├── renderer.py         全部绘制（五套界面）
│   ├── app.py              状态机、事件处理、动画推进
│   ├── view.py             逻辑画布 ↔ 真实窗口的缩放换算
│   └── audio.py            音效合成与播放（纯代码生成波形）
├── tools/
│   ├── verify_levels.py    关卡可通关性校验
│   ├── gen_levels.py       反向放置生成可解布局
│   ├── run_tests.py        自动化测试 + 报告导出
│   ├── capture_screenshots.py  自动生成界面截图
│   └── make_gif.py         自动生成演示 GIF
└── docs/
    ├── screenshots/        界面截图与演示 GIF
    ├── test_report.md      测试报告
    └── blog.md             本博客草稿
```

拆成这些模块的主要考虑是**复用**：把 `board.py` 独立出来后，游戏逻辑、求解器、测试脚本三处都调用同一套 `can_fly_out()`，不会出现三份实现口径不一致的问题。后来的两处改动也是同样的思路——`view.py` 把"坐标换算"从界面绘制里单独摘出来，`audio.py` 把音频设备相关的判断全关在一个模块里（初始化失败就整体静默），这样界面代码不必关心窗口缩放，调用方也不必每次播放前判断有没有声卡。

### 4.2 四次代表性协作（展开说明）

#### ① 路径检测：AI 一次写对，人工的价值在"卡范围"和"验收"

**我的要求**：按作业给出的判定标准实现路径检测——只判断同一行或同一列、箭头与边界之间是否还有其他箭头，并且要处理好边界情况。

**AI 的实现**：`can_fly_out()` 从箭头下一格出发沿朝向逐格前进，遇到箭头返回被阻挡、走出棋盘返回畅通；越界判断抽成 `is_inside()` 作为循环条件，四个方向的边界处理收敛到一处。

**效果**：逻辑正确，1×1 棋盘和贴边朝向棋盘外的情况都通过，没有出现越界异常。

**人工修改**：**这一版代码我一个字都没改**——AI 一次就写对了。我的参与在两个地方：

- **需求侧卡范围**：明确它只需要管同行同列到边界，没让它顺手加斜向判断之类的"额外增强"。作业写了"本次作业只要求实现上述基础点箭头玩法"，多加的规则反而可能判为偏离要求。
- **验收侧要求证据**：没有因为"看着对"就采纳，而是要求补边界用例后再说。最终用 9 项用例（1×1 棋盘四方向、贴边朝外、阻挡不在同一行列）逐条确认全部通过。这批用例保留在测试脚本里，可以复跑。

**我的体会**：AI 写核心算法确实快，但它写得对不代表我确认它对了。**"逻辑看起来对"和"验证过它是对的"是两件事**，后者才是我需要负责的部分。

#### ② 关卡设计：AI 给了方法论，不只是给数据

**我的要求**：再设计 4 个难度递增的关卡。同时——作业把"关卡实际上无法通关"列为明确扣分项——要求给我一个能自动判断关卡有没有死锁的办法，不靠手工试。

**AI 的实现**：它没有直接丢几组坐标过来，而是先给了一条**规则推论**：消除箭头只会减少障碍，所以"能否飞出"是单调性质，因此贪心循环就能判定可解性。据此写出求解器；又进一步提出「反向放置」——从最后被消除的箭头倒着往棋盘上放，放置时保证它到边界之间没有已放置的箭头，这样构造出的布局必然对应一条合法通关顺序，**天然可解**。

**效果**：5 个关卡全部通过校验（8 / 10 / 10 / 14 / 14 个箭头）。生成器先产出 4000 个布局，用求解器独立复验**全部可解**——推导成立。这一步直接封死了作业的扣分项。

**人工修改**：

- **难度曲线由我定**：前 3 关手工设计，保证依赖关系一眼看得懂；后 2 关才从生成结果里上难度。生成器只管"可解"，不管"好不好玩"，这部分只能人判断。
- **关卡命名与主题由我定**：顺藤摸瓜 / 层层推进 / 从两端突破 / 四面楚歌 / 天罗地网。
- **复查生成结果**：候选里出现过"整块对称对峙"这类看着别扭的布局，挑选时避开了。

**我的体会**：这次协作里 AI 的价值不在"给出 5 个关卡"，而在**给出一条能证明关卡可解的推导**。前者我自己也能摆出来，但摆出来的关卡能不能通只能靠试；后者让"可通关"从一个需要人工验证的性质，变成了构造时就已经保证的性质。同样，这两个办法（校验 + 生成）也正好对应作业里"关卡要能通关"和"每个关卡都要试玩验证"两条要求——前者用程序保证，后者由我本人完成。

#### ③ 试玩反馈「按 R 没反应」：先复现再定性，最后发现是输入法

**我的要求**：本人试玩 5 关后反馈——"按 R 没效果啊"。

**AI 的处理**：它没有直接去改代码，而是先写了个临时脚本复现：往 pygame 事件队列里塞一个 `R` 的按键事件，再调用游戏的事件处理函数，实测三种场景。结果是——**结算界面按 R 确实会把状态从 `result` 变回 `playing`、棋盘恢复 8/8，游戏中按 R 也正常**。所以**代码逻辑本身没有问题**，是按键事件根本没送进程序。

继续定位，找到原因是 **Windows 中文输入法接管了键盘**：SDL 默认在窗口创建时启用文本输入，输入法处于中文状态时 `R` 这类键被用于组字，游戏收不到按键事件。修复方式是在入口调用 `pygame.key.stop_text_input()` 显式关闭。

同时它还给了一个**不依赖键盘的兜底方案**：把底部按钮行改成按状态生成，通关结算时由两个按钮变成三个——`主菜单 | 重玩本关 | 下一关`，鼠标也能重玩本关。

**效果**：21 项测试全通过（新增 T11 验证「重玩本关」按钮、T12 验证 R 键在两个界面都生效）。另外按我的反馈把飞出动画从 0.40 秒调到 0.55 秒。

**人工修改**：

- **问题是我试玩时发现的**，不是 AI 主动预见的——它是按作业要求把功能做完的，做完之后好不好用只有点过才知道。
- **动画快慢由我判断**，AI 只负责把我的主观感受换算成参数。

**我的体会**：这次最值得记的是排查顺序。AI 的第一反应是"检查代码有没有 bug"，实测之后才转向环境原因。**如果跳过"先复现",很容易改一堆没坏的地方，甚至把对的逻辑改坏**。另外我意识到一件事：输入法这类问题在我自己的环境里才出现，测试脚本是跑不出来的——**自动化测试能替代作业第 5 节的测试要求，但它替代不了我本人真正把游戏点一遍**。

#### ④ 试玩反馈「按得快就不结算」：AI 找到了比反馈本身更严重的问题

**我的要求**：本人试玩后反馈两点——音效"有点刺耳"；另外附了一张截图，失误已经显示 **11/3** 却还没结算，我说的是"一直错误的话只要你按得快他就不会重新开始"。

**AI 的诊断**：它没有去动失误计数——那个数字本身是对的——而是去查"为什么判定明明发生了，结算界面却不出来"。结论是 `on_click` 在游戏进行中**没有检查胜负是否已判定**：判定失败后不会立刻弹结算，而是先播完碰撞动画（0.34 + 0.20 秒），这段窗口里状态仍然是「游戏中」，于是**每一次误点都把倒计时重置回满值**——点得越快，倒计时越走不完，结算永远不会出现。这和"失误 11/3"完全对得上。

顺着这条线，它还发现一个我没注意到的隐患：判定失败后继续点，如果把剩余箭头点光，会命中 `remaining == 0` 的分支把结果改写成胜利——**失败会被点成胜利**。

**修复**：在 `on_click` 里加一道输入锁，胜负一定就立即屏蔽棋盘和辅助按钮。锁的位置有讲究——必须放在**底部按钮行判断之后**，否则结算界面的「重试本关」会跟着一起失灵。同时它把音效也重新调了一遍：振幅 0.42 → 0.24、包络起音放缓（原来是 0.1 秒的音 25 毫秒就到七成响度）、频段下移，并让每个音效**独占声道**（连点时不再叠加）。

**效果**：新增 T21 覆盖这个场景（失败路径、胜利路径、结算按钮可用性三个子检查），**测试 29 → 30 项全部通过**；并做了反向验证——临时删掉那道锁，T21 立刻失败而其余 29 项不受影响，说明这条用例确实指向该 bug。音效的量化结果是峰值降低 43%、过零率（高频成分）降低 20~31%。

**人工修改**：

- 问题由我试玩发现，而且**"按得快"这个线索只有真实的高频操作才会出现**——测试脚本按固定间隔点击，是撞不上这个窗口的；
- "刺耳"是纯主观判断，AI 听不到声音，只能由我给定性、它去把定性换算成参数；
- 调柔后音量档位合不合适，同样得我试听之后说了算。

**我的体会**：这次 AI 交回来的东西**比我提的问题多一点**——我只说了"按得快不结算"，它还找出"失败会被点成胜利"。我原本以为前者是失误计数的问题，实际上两者是同一处时序缺陷。这让我意识到，反馈问题时**把现象描述准**（说"按得快就不结算"，而不是猜"失误计数好像错了"）比猜原因更有用：准确的描述能让它找到真正的根因，而不是顺着我的猜测去改一个本来没坏的地方。

### 5.3 开发过程中发现并修复的问题

测试在开发中确实抓到过问题，下面是三次代表性记录：

**① 2 项用例 FAIL → 定性为用例写错而非逻辑错。** 排查后确认：`P03` 想构造"朝上的箭头被上方箭头挡住"，但字符画 `"^\nv\n."` 里第 2 行的符号写成了 `v`（朝下），实际测的是另一个方向；`T05` 在调用 `restart()` **之后**才读取 `game.result`，而重开会把结果清空，断言必然失败。两者都是**测试用例本身写错，游戏逻辑正确**。修正用例后全部通过，教训是：断言读取状态的时机要和被测函数的执行顺序对齐。

**② 一处漏改没被测出来 → 暴露出测试本身的缺口。** 加窗口自适应时，我对同一个文件并行发起了多次修改，后写入的那次基于旧内容覆盖了前一次，导致 `app.py` 的构造函数改动丢失、`renderer.py` 少了一个 `import`——**而当时已有的 26 项测试完全没报错**。原因是这套测试此前只覆盖逻辑层和点击链路，**从未调用过任何绘制函数**。据此补了 T19 渲染冒烟（四个界面各渲染一帧，用哨兵色判断画面有没有画满），并做了反向验证：把那行 `import` 临时删掉后 T19 立刻以 `NameError` 失败，而旧套件抓不到。教训是"测试通过"只能说明**被测到的部分**没问题，还要反问一句"它到底覆盖到没有"。

**③ 判定后连点不结算 → 同一个根因还带出一个"败转胜"的隐患。** 详细过程见 4.2 ④，这里只记结论：凡是"先置结果标志、延迟若干秒再切状态"的写法，都必须在这段延迟窗口里屏蔽输入，否则用户的高频操作可以无限推迟状态切换。另外，写对应的测试要用**细小的时间步去连续冲击这个窗口**，按固定的大间隔点击反而撞不上——这也是它当初能躲过自动化测试的原因。

### 5.4 本人试玩记录

作业第 1 节要求"每个关卡都应由本人实际试玩，确保存在合理的通关顺序"。这部分不是脚本能替代的，我把实际试玩的情况如实记录如下：

| 试玩轮次 | 试玩范围 | 发现与结论 |
| --- | --- | --- |
| 第 1 轮 | 最初完成的 5 个关卡 | 5 关均可顺利通关，未出现中途卡死或找不到可点箭头的情况，确认每关都存在合理的通关顺序 |
| 第 2 轮 | 加入关卡选择与「继续游戏」之后的版本 | 新流程可用；提出两点改进：**飞出动画偏快，想看慢一点**；**键盘 `R` 按了没反应** |
| 第 3 轮 | 修复输入法、调整动画速度并新增「重玩本关」之后的版本 | 本轮提出新问题：**窗口顶部文字被裁掉一半，而且窗口拖不动**（附了截图） |
| 第 4 轮 | 加入撤销 / 提示、窗口自适应与音效之后的版本 | 撤销和提示可用；本轮提出两个新问题：**音效有点刺耳**；**失误达到上限后，只要点得快就不会弹出结算界面**（附截图显示失误已到 11/3） |
| 第 5 轮 | 修复上述两个问题之后的版本 | 确认撤销、提示、音效、连点恢复四项均正常；另复验前两轮的修复——键盘 `R` 能正常重开本关；窗口自适应生效，标题「第 2 关 · 层层推进」完整显示、标题栏可见且能拖动窗口 |

**试玩中发现并已修复的问题**

| 反馈 | 定位 | 处理 |
| --- | --- | --- |
| 进入游戏后没有回主页面的途径（第 1 轮提出） | 交互缺口 | `Esc` 改为逐级返回，底部增加「主菜单」按钮 |
| 飞出动画偏快（第 2 轮提出） | 主观手感问题 | `FLY_OUT_DURATION` 由 0.40 秒调整为 0.55 秒 |
| 按 `R` 没反应（第 2 轮提出） | 实测确认代码逻辑正确（脚本复现下按 `R` 确实会重置本关），真正原因是 **Windows 中文输入法接管了键盘**，按键事件没送进程序 | 入口调用 `pygame.key.stop_text_input()` 关闭输入法接管；同时把结算界面按钮扩为三个，鼠标也能「重玩本关」（第 5 轮复验通过） |
| 窗口顶部文字被裁、窗口拖不动（第 3 轮提出） | 实测屏幕可用区域只有 1920×1032，而窗口高 1280，**高出 248 像素**——系统把整窗上移，标题栏被顶到屏幕外。两个现象同一根因 | 新增 `view.py`：逻辑画布固定 720×1280，窗口按屏幕可用高度等比缩放（本机变为 554×984），鼠标坐标反向换算（第 5 轮复验通过） |
| 音效刺耳（第 4 轮提出） | 三个原因叠加：振幅偏大、包络起音太陡、频段偏高；此外快速连点时同名音效会叠加播放 | 振幅 0.42 → 0.24；包络改为淡入 + 二次衰减；频率下移；每个音效独占一个声道 |
| 失误达上限后点得快就不结算（第 4 轮提出） | 胜负已判定但"判定 → 弹出结算"之间存在动画延迟窗口，该窗口内没锁输入，每次误点都把倒计时重置 | 判定后立即锁定棋盘与辅助按钮（见 4.2 ④） |

**说明**：第 3 轮到第 5 轮都是针对"只在真实窗口下才出现的问题"安排的复验——输入法接管键盘、窗口超出屏幕、连点不结算，这三类问题在无头的自动化测试里都复现不出来，只能靠本人实际点一遍。六个问题的处理结果分级记录如下：`R` 键失灵、窗口超屏、音效刺耳、连点不结算四项均在第 5 轮**得到明确复验**；返回途径缺失与飞出速度两项在此后轮次中未再复现。

| 任务 | 预估耗时（小时） | 实际耗时（小时） | 差异（小时） |
| --- | --- | --- | --- |
| 需求分析与游戏设计 | 1.0 | 0.8 | -0.2 |
| Python 与图形库学习 | 1.5 | 0.5 | -1.0 |
| 游戏界面实现 | 3.0 | 2.0 | -1.0 |
| 路径与碰撞逻辑实现 | 2.0 | 1.0 | -1.0 |
| 关卡设计 | 2.0 | 1.0 | -1.0 |
| AIGC 辅助开发 | 4.0 | 3.5 | -0.5 |
| 测试与修改 | 2.0 | 1.5 | -0.5 |
| README 与博客撰写 | 1.5 | 1.5 | 0 |
| **合计** | **17.0** | **11.8** | **-5.2** |

**差异分析**：

- **节省最多的是"图形库学习"和"界面实现"**。原以为要花不少时间查 pygame 的 API 和布局方法，实际大部分时间花在描述需求和验收效果上，具体代码由 AI 产出。差别最大的是碰撞动画这类原本要反复试参数的活儿，改成口述效果即可。
- **"路径与碰撞逻辑"比预估省一半**，核心算法 AI 一次写对。
- **关卡设计没有省那么多**，因为难度曲线、主题命名、布局美观这些判断还是要自己做，AI 只解决了"可解性"这个技术问题。
- **"测试与修改"这一项反而没有明显减少**。虽然测试用例是自动生成的，但定位 2 个 FAIL 的根因、判断"是逻辑错还是用例错"，以及试玩发现输入法问题，这些都需要人来判断。
- **总耗时比预估少约 30%**。但要说明的是：AIGC 省的是**敲代码和查 API 的时间**，**需求拆解、方案取舍、结果验收和真正把游戏试玩一遍这些环节，AI 替代不了**，省下的时间也没有转移到这上面去。

## 七、心得体会

**一、AIGC 帮我越过的主要是"我不知道怎么写"，不是"我不知道要什么"。**

这次开发里 AI 效率最高的几处——路径检测、界面绘制、测试脚本——共同点是**需求已经很清楚**。我明确说了要做什么、边界在哪，它就能给出可用代码。反过来，最难的部分是"继续游戏要不要做解锁限制""动画多快算舒服""难度曲线怎么排"，这些没有标准答案，AI 也能给方案，但方案好不好只能自己判断。所以我的实际感受是：**AI 把"实现"这一段的成本压得很低，"定义问题"和"判断结果"这两段反而变得更关键了。**

**二、它给的最有价值的东西，有时不是代码，而是推导。**

关卡那一节最典型。我原本的需求是"再设计 4 关"，如果 AI 只是给了 4 组坐标，我依然不知道它们能不能通关，只能一关关试。它给的是"消除只有减少障碍、所以可飞性单调"这条推论，于是可解性从"需要验证的性质"变成了"构造时保证的性质"。这让我意识到：**向 AI 提要求时，说清楚"我真正想解决的困难是什么"比说清楚"我要什么东西"更重要。** 我提的其实是"我怕设计出通不了的关卡"，它才给出了方法论而不只是数据。

**三、"先复现再改"这个习惯，救了我一次。**

按键失灵那次，如果没有先写脚本复现，很容易直接去翻 `R` 键的代码——而那段代码其实是对的，改了反而可能把对的逻辑改坏。真正的病因在窗口外（输入法）。这件事让我明白：**报错或者"没反应"的时候，第一件事是确认它到底有没有发生，而不是猜哪里写错了。** 这条习惯我以后调试会一直用。

**四、AI 会写错，我的活是发现它错在哪。**

测试那 2 项 FAIL 是个好例子：报错信息看起来像"功能坏了"，但实际是测试用例自己写错了（方向符号写错、断言读状态的时机不对）。如果我当时下结论"游戏有 bug"然后去改游戏逻辑，就会把正确的东西改坏。**能区分"是功能错了还是验证方式错了"，这是在 AI 辅助开发里最需要练的能力。**

**五、过程记录的价值比我预想的大。**

开发时我让 AI 每完成一件事就当场在 `DEVLOG.md` 里记一条，当时只觉得是为了写博客方便。写完博客才发现，这份记录真正的用处是：**它逼我在每一步都想清楚"我到底改了什么、为什么改"**。回头看，「返回主菜单」「继续游戏与关卡选择」「按键与动画调整」这三次改进都是试玩后我自己提出来的，不是 AI 主动加的——这说明真正决定游戏好不好玩的，是我实际去用它，而不是把它写完。`DEVLOG.md` 如实记下了这一点。

**六、做得不够的地方。**

- 附加功能做了「关卡选择 / 继续游戏 / 撤销 / 提示 / 音效」五项，「保存游戏进度」和「打包 exe」没做。做哪几项是先按成本排过序的，优先选了能直接改善操作手感的部分；但基础功能的完整性和正确性，始终排在堆附加分前面——这一条到后面也没变。
- 游戏进度只存在内存里，关掉程序就重置。作业附加分里有「保存游戏进度」这一条，我没做，这是个明确的缺口。
- 自动化测试后来补上了渲染冒烟，但仍然跑不了真实窗口：输入法接管键盘、窗口超出屏幕、判定后连点不结算，这三类问题全都是在真实试玩中才暴露出来的。这也是为什么"本人试玩"这一步不能省。
